# AGENTS.md

Flog is a personal blog and small CMS: Flask 3, SQLAlchemy 2, Jinja2, vanilla JS and CSS (no frontend build step). The public site and the admin live in one app. `README.md` has the feature list, setup, environment variables and deployment; this file covers what is easy to get wrong.

## Commands

Use the project virtualenv (`.venv/bin/python`, Python 3.14). `./scripts/bootstrap.sh` creates it.

```bash
.venv/bin/python -m pytest tests -q -k <keyword>   # full suite is ~1000 tests, ~2 minutes: run targeted tests first
node --test tests/*.test.js                         # frontend tests
flask db upgrade                                    # apply migrations
flask translate compile                             # rebuild messages.mo after editing messages.po
```

## Layout and wiring

- `app/__init__.py` creates the global `app`, `db`, `login`, `mail`, `csrf` objects. Modules do `from app import app, db` and register routes or hooks as an import side effect, so a new module that registers a route, `after_request` hook or CLI command must be added to the import line at the bottom of `app/__init__.py`. Use that same file to see how `routes`, `static_cache`, `font_preload` and `cli` are wired.
- `app/routes.py` holds the public routes. `app/admin/` is the `/admin` blueprint, one module per area (`posts`, `pages`, `images`, `mail`, `users`, `settings`, ...).
- Business logic lives in plain modules, not in views: `post_drafts.py` (drafts and revisions), `comments.py` and `comment_mail.py`, `images.py` and `live_photos.py` (upload, compression, resized variants, HEIC and Live Photo video), `pages.py`, `search.py` and `search_index.py`, `likes.py`, `post_views.py`, `authorization.py`.
- `app/content.py` renders Markdown (with `markdown_extras.py` for task lists and math), and `app/security.py` sanitizes all rendered HTML with bleach. Anything that outputs user content goes through them; do not mark user input as safe elsewhere.
- Roles are only `user` and `admin` (`User.is_admin`). Admin views use `admin_required`.
- Templates: `app/templates/` (`base.html` is the public shell, `admin/base.html` the admin shell, `email/` the HTML mail shell). Static files: `app/static/`; the Vditor, KaTeX and Mermaid builds under `static/vendor/` are vendored and pinned, so do not edit them.

## Conventions

- Configuration comes only from environment variables / `.env` through `config.py`. There is no admin page for env settings. A new setting needs an entry in `config.py`, `.env.example` and the README environment table.
- Database: SQLite locally, MySQL/MariaDB in production. Write portable SQLAlchemy; the SQLite-only FTS5 search index has a `LIKE` fallback. Datetimes are stored in UTC and shown in `DISPLAY_TIMEZONE`. Every schema change needs an Alembic migration (`flask db migrate`, then read and fix the generated file).
- The site is Chinese only. Message ids in code and templates are English and the Chinese text lives in `app/translations/zh/LC_MESSAGES/messages.po`. Both `.po` and the compiled `.mo` are committed, so run `flask translate compile` after editing the `.po`. Site wording an admin can change is in `site_text.py`.
- Article fonts (`app/static/fonts/`) are subsetted files generated by `scripts/generate_article_fonts.py`. Change the generator rather than hand-editing `article-fonts.css`, and note it needs network access. `font_preload.py` injects `<link rel="preload">` for the pieces a page needs; `static_cache.py` makes fonts and vendored folders cache for a year (the site's own CSS and JS keep revalidating).
- Frontend JS is plain scripts loaded with `<script>`. The Node tests run a script inside `vm` with hand-made `document` and `navigator` stubs, so a script should not assume more globals than its test provides.
- Commit messages use conventional prefixes (`feat(scope):`, `fix:`, `perf:`, `refactor:`, `test:`, `docs:`).

## Tests

- `tests/conftest.py` sets `SECRET_KEY` and an in-memory SQLite database before importing the app, and its fixtures (`application`, `client`, ...) create and drop tables per test. Reuse them and the existing helper fixtures (for example the mail outbox) instead of building new setup.
- `tests/test_public_repo_hygiene.py` scans every tracked text file and fails if it contains local machine paths (such as a home directory) or the author's personal analytics IDs. Never put either in a committed file, docs included.
- Some tests pin documentation and assets (README environment table, font CSS, vendored files), so a change there can fail a test even though no code changed.
- MySQL runs need `TEST_DATABASE_URL` pointing at a local database whose name ends in `test`; see the README.

## Git and deployment

- `origin` is the public repository (GitHub `Flog`); production follows `origin/main`. A `private` remote also exists, so push explicitly to `origin`.
- Deploy with `./scripts/deploy.sh --dry-run`, then `./scripts/deploy.sh`, only after `git push origin main` and only when the user asks. The script backs up the database, uploads and `.env`, ships the commits over SSH, migrates, restarts and smoke-tests. Do not edit the server by hand.
- Do not commit `.env`, `instance/`, `logs/`, databases or uploads (all git-ignored). Do not run destructive commands against `instance/`, which holds the local database and uploads.
