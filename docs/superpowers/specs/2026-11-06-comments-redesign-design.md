# 评论系统改造设计

日期:2026-11-06

## 背景与目标

现在的评论是「昵称 + 邮箱,发布即显示」:没有回复、没有审核、没有防刷,后台评论页只是一个只能删除的简单列表,评论也只能挂在文章上。

本次改造:

1. 支持回复(两层)。
2. 审核与防垃圾:首次评论需审核,通过后免审;加限流与蜜罐。
3. 评论正文支持受限 Markdown。
4. 后台评论管理增强。
5. 评论可挂在文章或内容页上,并可按文章或页面分别开关。
6. 表情(emoji)选择器:评论框和后台富文本编辑器共用,所有平台统一显示 Noto 样式。

**不做**:邮件通知(邮件功能整体将另行统一改造)、登录评论、编辑自己的评论。评论者身份保持匿名(昵称 + 邮箱,邮箱仅用于头像和弱信任判断)。

## 1. 数据模型

`PostComment` 改动(一个 Alembic 迁移):

| 字段 | 说明 |
| --- | --- |
| `post_id` | 改为可空 |
| `page_id` | 新增,可空,外键 `Page.id`,`ondelete=CASCADE`,有索引 |
| `parent_id` | 新增,可空,自引用外键 `PostComment.id`,`ondelete=CASCADE` |
| `status` | 新增,`'pending'` 或 `'approved'`,检查约束;迁移时已有评论全部设为 `approved` |
| `user_id` | 新增,可空,外键 `User.id`,`ondelete=SET NULL`;站长登录后评论时记录 |
| `ip_hash` | 新增,可空,带索引;沿用 `app/likes.py` 的加密哈希方式,只存哈希 |

- 检查约束:`(post_id IS NOT NULL) <> (page_id IS NOT NULL)`,即评论有且只有一个归属。
- `body` 存 Markdown 原文,显示时渲染。长度上限仍为 1000。
- `Post.comments` 与新增的 `Page.comments` 关系都带 `cascade='all, delete-orphan'`。

`Post` 和 `Page` 各加 `comments_enabled`(布尔,非空):

- 已有文章及新文章默认 `True`,保持现状。
- 页面默认 `False`。迁移的 `server_default` 与模型默认值保持一致。

## 2. 回复层级

只有两层:顶层评论,以及挂在顶层评论下面、按时间平铺的回复。

- 回复某条回复时,`parent_id` 仍指向它所在的顶层评论,正文开头自动带上 `@昵称`。
- 提交时校验 `parent_id`:必须存在、属于同一个归属对象、已通过审核。如果它本身是回复,则归到它的顶层评论。
- 删除顶层评论会级联删除其下所有回复(后台删除前给出确认)。

## 3. 受限 Markdown

- 允许:粗体、斜体、行内代码、代码块、引用、列表、链接。
- 不允许:图片、标题、原始 HTML。
- 链接统一加 `rel="nofollow ugc noopener"` 和 `target="_blank"`。
- 渲染后用现有 `app.security.sanitize_html` 再过一遍,白名单标签要比文章更窄。
- 评论渲染放在新的小模块里(例如 `app/comments.py`),不扩充 `app/content.py`。

## 4. 审核与防垃圾

提交评论的判定顺序:

1. 所属对象不存在、未发布或 `comments_enabled` 为假:直接拒绝(403/404)。
2. 蜜罐字段非空、或表单渲染到提交的耗时过短:静默丢弃,返回与成功相同的页面,不入库。
3. 按 `ip_hash` 限流(每分钟、每小时各一档),超限拒绝并提示稍后再试。
4. 与同一 `ip_hash` 最近的评论正文相同:拒绝(重复内容)。
5. 决定 `status`:
   - 站长已登录:`approved`。
   - 同一邮箱此前有 `approved` 评论,且正文链接不超过 2 个:`approved`。
   - 其他情况(首次评论,或含 3 个及以上链接):`pending`。

邮箱由访客自己填写,可以被冒用,所以「免审」只是弱信任,不是身份认证。站长自己的邮箱发过的评论不算「已通过的邮箱」,不会给其他人带来免审资格。

访客提交成功后,`approved` 的评论直接定位到评论区;`pending` 的评论只提示「已提交,审核通过后显示」,不向其他访客展示。

## 5. 评论开关

- 页面的编辑表单里有「允许评论」复选框;文章在列表页和编辑页各有一个「关闭评论 / 开启评论」按钮,点击立即生效,不走草稿与发布流程。
- 关闭后:
  - 前台不显示发表表单和回复按钮。
  - 已有的 `approved` 评论仍以只读方式展示,标题旁标注「评论已关闭」;一条评论都没有时,整个评论区隐藏。
  - 提交端点在服务器侧再检查一次开关。
  - 待审评论不受影响,站长仍可通过、删除;站长不能回复已关闭的内容。
- 关闭评论不删除任何数据,重新打开后一切照旧。
- 评论只接到内容页(`kind='content'`)。

## 6. 前台

- 评论区从 `post/post.html` 抽成可复用的片段,文章页和内容页(`page/content.html`)共用。
- 评论计数只算 `approved`。
- 点「回复」后表单留在原位,显示「回复 @某人 取消」,并滚动聚焦到输入框;没有 JS 时「回复」是 `?reply=ID#comment-form` 链接,效果相同。

## 7. 后台

- 评论页分「待审核」「已通过」「全部」三个标签。
- 筛选:按文章或页面;搜索昵称、邮箱、正文。
- 操作:单条或批量通过、删除;站长在后台直接回复(自动 `approved`,记录 `user_id`)。
- 列表新增「所属」列,链接到对应文章或页面;回复标明被回复的对象。
- 仪表盘的评论数旁显示待审数量。

## 8. 表情(emoji)

**存储**:始终存 Unicode 字符,不存图片地址或短代码。评论正文的 Markdown 渲染与 `sanitize_html` 不需要改动。

**统一样式**:用 Noto Emoji 的图片(Apache 2.0)统一各平台的显示,不用 Noto 字体。原因是 Safari 对 Noto 彩色字体格式的支持不可靠,图片在所有浏览器上表现一致。图片用 72 像素的 PNG 而不是 SVG:同一批 1407 个表情,PNG 共 3.7 MB,SVG 要 13.8 MB,超出 8 MB 的体积预算;最大显示尺寸 26 像素,72 像素在高清屏上足够清晰。

- 新增 `app/static/emoji.js`:在页面的评论正文、文章正文、页面正文里,把文本节点中的表情替换成 `<img class="emoji" alt="😀" draggable="false">`,`alt` 保留原字符,复制出来仍是表情。
- 没有 JS 或图片缺失时退回系统表情。
- 只替换已打包的表情,未打包的保持系统样式。
- 静态文件放在 `app/static/emoji/noto/`,文件名按去掉 `FE0F` 的小写十六进制码点命名(如 `1f600.png`),附 Apache 2.0 许可文件和 NOTICE;由 `scripts/build_emoji.py` 从 Noto 仓库挑选并复制,同时产出 `emoji-keys.js`(哪些表情能替换)和 `emoji-data.js`(选择器的分类、中文名称与关键词)。许可文件取自 Noto 仓库 `2D/svg/LICENSE`(Apache 2.0);仓库根目录的 `LICENSE` 是字体用的 OFL,不是图片的。
- 打包范围:Unicode 全部「完整限定」表情,去掉国旗、肤色变体和 ZWJ 组合,共 1407 个,分八个分类(表情、人物、动物与自然、食物、旅行、活动、物品、符号)。中文名称与关键词来自 Unicode CLDR 的 zh 注释;没有中文注释的退回英文名。数据版本记在 NOTICE 里。

**选择器**:一个共用组件 `app/static/emoji-picker.js`。

- 分类标签、搜索(中文关键词,来自 Unicode CLDR 的 zh 注释,生成脚本取数,具体来源实施时核实)、最近使用(存在 `localStorage`,读写包 try/catch)。
- 评论框:输入框旁一个表情按钮,弹出面板,点选后在光标处插入(`setRangeText`),焦点留在输入框;支持键盘操作与 Esc 关闭。
- 后台编辑器:在现有 Vditor 工具栏里,和「图片库」一样加一个自定义按钮,选中后调用 `vditor.insertValue`。不用 Vditor 自带表情面板,以便两处共用同一份数据和同一个样式。
- 面板里显示的也是 Noto 图片,与最终页面一致。编辑器编辑区里的表情是系统样式,发布后的页面才是 Noto 样式。

**编辑区的表情样式(实验项,逐步调试)**:默认编辑区保持系统样式,发布前用现有文章预览确认最终效果。

- 不在编辑区里替换 DOM。Vditor 的 IR 模式靠读 DOM 还原 Markdown,把表情换成 `<img>` 可能被存成 `![😀](...)`,污染正文,也会影响光标、撤销和输入法。这是对 Vditor 工作方式的判断,尚未在 4.0.1 上实测。
- 实验做法:只给编辑区的表情字符指定 Noto Color Emoji 网页字体(`@font-face`,按表情的 `unicode-range` 限定),不改 DOM。
- 已知风险:Safari 对 Noto 彩色字体格式的支持不可靠,可能退回系统表情。不为 Safari 另做字体子集。
- 成功标准:Chrome 和 Firefox 的编辑区显示 Noto 样式,Safari 至少不出现缺字或方框,且 `field.value` 与未启用字体时完全一致。
- 实验通过才保留;不通过就删掉字体文件和样式,不影响选择器、评论区和发布后页面。实验结果记录在计划里,不回写本节之外的设计。
- **实验结果:通过,保留。** Chrome、Firefox、Safari 的编辑区都显示 Noto 样式,且是彩色字形(Safari 用画布逐像素比对确认过)。字体用 Noto-COLRv1-noflags 裁剪成 WOFF2(约 1.1 MB,OFL 授权,许可文件随字体放在 `app/static/fonts/`)。唯一的坑:`unicode-range` 和字体子集必须包含 `U+FE0F`(变体选择符),否则 Safari 会把 `❤️` 这类序列整个交给系统字体。

**不做**:`:短代码:` 输入联想、自定义表情上传、表情反应(点赞式)。

## 9. 测试

- 迁移:升级后已有评论为 `approved`,`post_id` 保持不变;降级可执行。
- 模型:归属约束、`parent_id` 同归属校验、级联删除。
- 提交流程:开关关闭拒绝、蜜罐、限流、重复内容、首次审核与免审、站长直接通过、链接数量阈值。
- Markdown:允许与不允许的标签、链接属性、XSS 样本。
- 前台:关闭时的只读展示与隐藏、待审评论不可见、回复表单。
- 表情:生成脚本产出的数据与静态文件一一对应(没有悬空引用);页面引入 `emoji.js`;许可文件存在。
- 编辑区字体实验:启用前后提交的 Markdown 文本一致(编辑区样式不能改变正文内容)。
- 后台:标签、筛选、搜索、批量操作、回复受开关约束。

## 10. 实施顺序建议

按能独立上线的单元拆分,每个单元自己有测试:

1. 数据模型与迁移(含 `comments_enabled`)。
2. 评论服务模块:Markdown 渲染、审核判定、限流。
3. 前台:共用评论片段、回复、文章页与内容页接入。
4. 后台:评论开关、评论管理页重做。
5. 表情:生成脚本与静态资源、`emoji.js` 替换、选择器组件、评论框和 Vditor 接入。
6. 编辑区表情字体实验(可选,独立于第 5 步,可单独回退)。
